01 · The method

Design is the goal you give

An agent optimizes whatever goal it is handed. So the goal is the design outcome — the feature is a constraint it must satisfy.

The problem

Two things go wrong

Quality suffers

The agent optimizes for the feature working, so the architecture is whatever falls out — not chosen.

Knowledge is lost

Decisions made while building never reach the next session, which re-derives or contradicts them.

The loop

Two roles, two moves

The Guide

Chooses one design outcome at a time; never writes code. Deliverable: design quality across the product's evolution.

The Worker

A capable engineer that designs and builds it, with the behavior as a constraint, and returns its reasoning.

Direct — hand the right goal.  Measure — observe honestly what came back.  No enforcement pillar: review measures and feeds the next direction, it never coerces.

Interfaces are positive; under-structuring is the graver risk. The dominant failure of unguided generation is too little structure — flat code, literals, unowned rules. So name a seam by default: an unused one is a light cost, a missing one forces a reopen. §9 and §13 are the two that can cap a whole design.
Two kinds of task

Designing, and changing what exists

Building from nothing and changing code that already works are different tasks, with different risks — so aims has a checklist for each. The 18 principles above are for the blank file; a companion, add-feature-principles.md, is for the change.

Greenfield design

The danger is too little structure. Reach for a seam by default; name the owners; make each principle hold by construction. Front door: /aims-plan.

Changing existing code

The dangers are silent behavior drift, scattering a rule while patching it, and bolting the requirement on instead of absorbing it. Characterize the behavior first, then make the change easy, then make the easy change. Front door: /aims-add-feature.

The measure is a before/after review on the target's own grain — no design regression, ideally a small improvement, and across successive changes the trajectory (rot is cumulative). And consistency beats dogma: match the code's existing style and abstraction even against a principle — importing a foreign style (value objects onto bare-int code) is itself a regression. The goal is no new mess, not conformance to the list.
