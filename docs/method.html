01 · The method

Design is the goal you give

An implementing agent optimizes toward whatever goal it is handed. So if you want good design out, the design has to be the goal — with the feature attached as a constraint it must satisfy.

The problem

Two things go wrong when an agent writes code

Quality suffers

The agent optimizes for the goal it was given — get the feature working — so the architecture is whatever happens to fall out of that, not something anyone chose.

Knowledge is lost

Insights and decisions made while building do not reach the next session, so later work re-derives them from scratch, or contradicts them.

Two roles

The Guide and the Worker

Separating who decides what to optimize from who executes is what lets the design be the goal.

The Guide

Holds the product vision and decides, one at a time, the design/quality outcome the codebase most needs next — never writing implementation code. Its deliverable is the design quality across the product's whole evolution, not features shipped or code volume.

The Worker

A capable engineer that receives that outcome as its objective, with the behavior as a constraint the design must satisfy, and designs and builds it — returning its reasoning so the Guide can evaluate the design, not just whether it runs.

Direct and measure — no coercion. The method has exactly two moves: hand the right goal, and observe honestly what came back. There is no enforcement pillar — a design is made good at construction time by the goal you set; review only measures whether it was reached and feeds the next direction. The one thing that must be robust is that the goal keeps reaching the Worker.
What "good" aims at

One source of design principles

A single document is used both to build and to grade — the principles are identical for every side, only the how differs. Asking for one thing and measuring another is the failure this avoids.

§18 names the canonical principles this set already carries under other names — Open/Closed, Liskov, Acyclic Dependencies, DRY, Least Astonishment, YAGNI. Correctness (§13) and single-owner (§9) are the ones that can cap a whole design — the precondition the rest serve.

Interfaces are positive; under-structuring is the graver risk. The dominant failure of unguided generation is too little structure (flat code, literals, primitive obsession, unowned rules); over-engineering is a lighter, secondary fault. So a class exposes a generic domain surface by default, and when unsure whether to name a seam you name it — an unused seam is a light cost, a missing one forces a reopen. A type is judged by its shape, never by predicting a second implementation.

Knowledge that survives the session
