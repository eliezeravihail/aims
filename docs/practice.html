How the loop actually runs

The Guide drives one loop, round after round, until the current change is delivered. Each round chooses one objective, delegates, measures, and chooses again from the evidence — the sequence is never planned up front.

The operating loop

One round, five moves

  1. Ground the product by asking

    Surface open product decisions, and the day-zero foundational substrate — the language, framework, base deps whose replacement would rewrite everything — which is asked of the user, never defaulted. If a new product rests on an unproven premise, objective one is a spike that proves it before designing on top of it.

  2. Choose one design objective

    Feature-scoped, framed around design quality, with exit criteria derived adversarially: the edge and break cases named (empty / one / many, cross-boundary, ordering, the absent-optional) so a minimal implementation cannot satisfy it on paper.

  3. Delegate a bounded handoff

    The Worker gets the design outcome, the behavior it must satisfy, the principles as the target (not a checklist), and the testing discipline — never a pre-made design. Two strong engineers given the handoff should be free to reach genuinely different, equally good designs.

  4. Measure, then one mandatory revise round

    Score against the criteria; run the subtractive pass (cut what pays for nothing) and the concept-fit pass (is each element the kind of thing it is). A design objective is never read as met on its first pass: hand the findings back and have the Worker revise once. Iteration is the largest quality lever the experiments found.

  5. Choose again from the evidence

    Continue an unmet criterion, implement the next capability, simplify, or deliberately accept a justified cost. There is no fixed phase order.

Two ways to run it

Automatic or stepped

Automatic

The Guide drives the whole loop end to end and pauses only at the two legitimate human moments — an open product decision it must not guess, and receiving the next product change. A returning Worker auto-advances the loop.

Stepped

For hands-on supervision: the loop stops at every phase boundary (plan → build → review) and advances only on an explicit command, so you inspect and edit between phases. Same loop, a stricter stop-policy.

The loop's position lives in .aims/state.md — run-state only, reloaded at the start of every command — so the goal survives side-conversations and context compaction. Nothing runs in the background; aims is engaged only through its commands.

How quality is measured

The assessment form

Each principle is scored 0–10, and the score is derived from a handful of binary structural sub-checks rather than eyeballed — which is what keeps a re-run reproducible and absorbs judge noise.

STEP 0

Fixed inventory

Pin the rules (R), change-axes (X), and acceptance cases (C) from the spec — never from a design. Identical for every judge and every arm.

PER PRINCIPLE

Sub-checks → score

Decompose into binary structural checks, each cited. score = 10 × passed / applicable. Any score below 10 requires a cited finding.

SEVERITY

Weight & cap

The worst failed check sets the weight (×1…×8) and a ceiling. A §13 correctness or §9 ownership fault can reach S4 and caps the whole design.

Two projections, one form

The full scored form + aggregate profile is the measurement/judging layer, for comparing arms. The operational review in the loop is the same form's score-less projection — the sub-10 findings sorted most-severe-first, each cited, no aggregate grade — so the review stays a direction-feeding findings list, faithful to "never a score".

Reliable, not a benchmark

The form is a reliable instrument (same design → same profile), not an externally valid benchmark — none exists for design quality, and deterministic metrics measure a different construct (surface volume). aims triangulates it with change-survival and static metrics as separate signals. Documenting & preserving

Records co-located with the code

The one directory structure is both the code graph and the knowledge tree — so knowledge is reached by navigating to the file or root record in front of you, never by reading the whole project.

Companions & root records

A source file with something worth recording gets a <file>.md companion beside it (Insights / Decisions / Discussions). Cross-cutting knowledge lives at the root: goals.md, architecture.md, base-dependencies.md, dependencies.md, and decisions/ ADRs.

Anchored, so drift is detected

A companion is anchored to its same-named source by a content hash. When a later session reads a companion whose source changed, one advisory hook says "re-verify" — it never blocks. decisions/ are append-only: to change one you add a superseding entry, never rewrite.

What aims deliberately does not have: no memory tree, no consolidation/doctor/lint machinery, no write hook, no planning lock. Relevance is structural — navigate the co-located records — so nothing needs to be kept coherent between turns. The one read-time advisory is the whole of the active machinery.
