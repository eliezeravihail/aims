02 · In practice

How the loop runs

One round, five moves — repeated until the change is delivered. The sequence emerges from the evidence, never planned up front.

The operating loop

Five moves

  1. Ground by asking

    Surface open product decisions and the foundational substrate (language, framework, base deps) — asked, never defaulted. An unproven premise gets a spike first.

  2. Choose one objective

    Feature-scoped, framed as a design outcome, with exit criteria named adversarially (the edge and break cases).

  3. Delegate a bounded handoff

    The design outcome, the behavior as a constraint, the principles as target — never a pre-made design.

  4. Measure + one revise round

    Score, run the subtractive and concept-fit passes, hand the findings back once. A design is never met on its first pass. How it's scored →

  5. Choose again from the evidence

    Continue, extend, simplify, or accept a justified cost. No fixed phase order.

Two ways to run

Modes

Automatic

Drives the whole loop, pausing only for an open product decision or the next product change.

Stepped

Stops at every phase (plan → build → review) for inspection. Same loop, stricter stops.

The loop's position lives in .aims/state.md — reloaded each command — so the goal survives compaction. Nothing runs in the background.

Documenting & preserving

Records beside the code

Where knowledge lives

A <file>.md companion beside a source file (Insights / Decisions / Discussions); cross-cutting records at the root (goals.md, architecture.md, decisions/). Reached by navigating, not by reading the tree.

Anchored, not trusted

A companion is hashed against its source; on drift, one advisory hook says "re-verify" — it never blocks. decisions/ are append-only.

No machinery: no memory tree, no consolidation/doctor, no write hook, no lock. Relevance is structural; the one read-time advisory is all of it.
