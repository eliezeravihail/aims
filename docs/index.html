Make design the goal,
not what survives shipping.

When an AI agent writes code, it optimizes the goal it is handed. Give it a feature ticket and design quality becomes whatever falls out. aims hands the agent the design outcome as the goal — with the feature as a constraint it must satisfy — measures the result against one set of principles, and files the design knowledge beside the code so the next session continues instead of re-deriving.

Direct

Hand the Guide's design objective to a capable Worker, with the behavior attached as a constraint. Quality is built at construction time.

Measure

Score the returned design against the principles, feed the findings back for one revise round — never a gate, never coercion.

Remember

File insights and decisions as records co-located with the code. A later clean session reads them by navigating, not re-deriving.

The method

Two roles, one loop

The method has exactly two moves — direct and measure — and no enforcement pillar. A design is made good by the goal you set, and review only measures whether it was reached, feeding the next direction.

The Guide

Holds the product vision and chooses, one at a time, the design/quality outcome the codebase most needs next. Never writes implementation code. Its deliverable is the design quality across the product's whole evolution.

The Worker

A capable engineer that receives that outcome as its objective, designs and builds it, and returns its reasoning. The Guide then measures the design and chooses again.

  1. Ground the product by asking

    Surface open product decisions, and the day-zero foundational substrate (language, framework, base deps) — asked of the user, never defaulted. If a new product rests on an unproven premise, the first objective is a spike that proves it.

  2. Choose one design objective

    With sharp exit criteria — the edge and break cases named adversarially, so a minimal implementation cannot satisfy it on paper.

  3. Delegate, framed as a design outcome

    Bounded handoff to the Worker (or run inline), the behavior as a constraint — never a feature ticket.

  4. Measure, then one mandatory revise round

    Score against the criteria; run the subtractive and concept-fit passes; hand the findings back and have the Worker revise once before the design reads as met. Iteration is the largest quality lever the experiments found.

  5. Choose again from the evidence

    The sequence is not planned up front — direction emerges as the build proceeds. The loop's position lives in .aims/state.md, so the goal survives compaction and side-conversations.

What "good" aims at

One source of design principles

A single document — design-principles.md — is used both to build and to grade. The principles are identical for every side; only the how differs. Asking for one thing and measuring another is the failure this avoids.

Interfaces are positive; under-structuring is the graver risk. The dominant failure of unguided code generation is too little structure — flat procedural code, inline literals, primitive obsession, anemic bags, rules owned nowhere. Over-engineering is a real but lighter, secondary fault. So a class exposes only a generic domain surface (an interface, separate class or not), and when unsure whether to name a seam you lean toward naming it: an unused seam is a light, local cost, a missing one forces a reopen. Judge a type by its shape — is it a domain concept, or a concrete wearing a costume — never by predicting a second implementation.
How quality is measured

A standardized assessment form

Each principle is scored 0–10, and the score is derived from a handful of binary structural sub-checks rather than eyeballed — which is what keeps a re-run reproducible and absorbs judge noise. Severity does the rest.

STEP 0

Fixed inventory

Pin the rules (R), change-axes (X), and acceptance cases (C) from the spec — never from a design. Identical for every judge and every arm.

PER PRINCIPLE

Sub-checks → score

Decompose into binary structural checks, each cited. score = 10 × passed / applicable. A score below 10 requires a cited finding.

SEVERITY

Weight & cap

The worst failed check sets the weight (×1…×8) and a ceiling. A correctness (§13) or ownership (§9) fault can reach S4 and caps the whole design.

Two projections, one form

The full scored form + aggregate profile is the measurement/judging layer (comparing arms). The operational review is the same form's score-less projection — the sub-10 findings sorted most-severe-first, each cited, no aggregate grade — so the loop stays a direction-feeding findings list.

Honest about what it is

The form is a reliable instrument (same design → same profile), not an externally valid benchmark — none exists for design quality. Deterministic metrics (coupling, complexity) measure surface volume, a different construct. So aims triangulates the form with change-survival and static metrics as separate signals that need not agree.

What was tested

Blind, controlled experiments

Every experiment is a controlled, blind-judged comparison — an aims arm against a rival or a no-method control, graded by separate judges against the same inventory — not a single-arm demonstration (PROTOCOL.md). Checkout is a three-way tie at the cap (no correctness or ownership faults in any arm). Marketplace: aims absorbs the new category with zero core edits where the others reopen existing owners. Ledger: a named return type vs a bare tuple — the difference deterministic metrics were blind to.

Read with the confounds — no single grade is a verdict. Every reading is n = 1 per product, judged by an LLM (±0.5 calibration noise), and the arms differ in maturity. aims' rank is product-dependent: strongest where change-absorption is the axis. The honest headline is the recurring shape across products and the reproducible instrument — not a win tally.
How to use it

Install & run

aims is a Claude Code plugin. Requirements: Python 3 (standard library only) and bash — nothing else.

1 · Install the plugin

/plugin marketplace add eliezeravihail/aims
/plugin install aims@aims

Makes the aims-guide skill and the /aims-* commands available in every session.

2 · Set up a project

/install-on .

Idempotent. Installs the two per-project hooks (session-start, and the read-time staleness advisory) plus the anchor tool under .aims/. Never touches your code.

Drive the design

  • auto/aims-plan-and-build "<task>" — runs the whole loop: discovery → design objective → build → review → file the records, pausing only for open product decisions.
  • step/aims-plan → /aims-build → /aims-review — supervised, phase by phase, with a plan report to read between phases.
  • any/aims-review <branch | diff | path> — measure any change on its own against the principles.
  • solo/aims-sharpen-prompt — the framing discipline on its own: turn a vague ask into a real brief before executing. Needs no project setup, not limited to software.
Knowledge lives beside the code. A companion <file>.md sits next to each source file (Insights / Decisions / Discussions); cross-cutting records — goals.md, architecture.md, decisions/ — live at the repo root. Records are anchored to their source, so a later reader is told to re-verify on drift. You reach knowledge by navigating, never by reading the whole tree.
