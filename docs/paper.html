Design as the objective

A model optimizes the goal it is given. Coding agents are given correctness, so structure is never the goal unless it is made one. We built a method that makes it the goal. We could not show that it helps.

Eliezer Avihail · September 2026 · full paper (PDF)

The idea

Why the goal must be explicit

A language model produces text one token at a time, choosing what is likely given the context. Preference training rewards answers that look like they satisfy the request, and agent loops stop when the task works. An instruction such as "write clean code" changes nothing, because it gives the model nothing it can fail. The paper's argument has three parts:

1 · Make it checkable

A goal becomes real only when it is a list of items, each of which can be answered yes or no for a given design.

2 · Check before the code

Once an interface is written, the model tends to defend it rather than revise it. So the check belongs inside the design step, against a written list rather than the model's own opinion. This part has not yet been tested directly.

3 · When in doubt, more structure

Most code a model learned from is ordinary working code. Too much structure costs a layer nobody uses; too little spreads, because every later change has to work around the missing boundary.

The method

Two tasks, one scored form

Aims serves two tasks: designing new code, and adding a feature to existing code without eroding its design. The latter is the process that Lehman, Parnas and others describe as software decaying under change. Both tasks use the same scored form, built only from checks drawn from the established literature that a reader can answer yes or no on a given design. There are 15 chapters for new designs and 12 for adding features.

  1. Lists from the specification.

    Before reading the design, the reviewer lists the rules the product must obey, its likely directions of change, and its acceptance cases. Every design of that product is checked against the same lists.

  2. Item by item.

    Each item is pass, fail or not applicable. A failure must point to a list entry or a named part of the design, and one defect counts once.

  3. Chapter scores.

    A chapter scores round(10 × passed / applicable), and its worst failure sets both its ceiling and its weight.

  4. Report.

    The report gives the weighted average, the worst chapter, the count of serious failures, and a gate: any correctness failure (S4) marks the design blocked. The grade is never capped and never reported alone.

The designer receives only the list of failures, without a score, and revises the design once before anything is built. For comparing designs, the full scored form is used.

Why not a metric

The automatic measures count size, not structure

Lines of code, cyclomatic complexity, Halstead and the Maintainability Index all measure size and branching. The paper tested them on one pair of implementations that differed in a single design choice, a named type against a plain tuple. Two of the metrics saw no difference, and two preferred the weaker design, because a named type adds lines without adding branches. A coupling count built for this work ranked that pair correctly. It still missed a fault whose cause was the choice of operation, which can only be seen against the specification. The paper found no automatic metric that can judge design quality.

The evaluation

Study 1: new designs, compared with OpenSpec

Both methods designed three services: feed ranking, booking availability and entitlements. The work was design only, with no code. D1 scores the first design; D2 scores the design after a new, unannounced requirement. OpenSpec ran as the installed tool (1.13.2), with each stage in its own session. The comparison ran twice on the same OpenSpec designs. In round 1 the Aims designs came from an earlier run and one judge scored each product. Round 2 reran Aims at its current version, in stricter isolation, and scored each product with two judges of opposite leanings.

  • measures The principle-free measure disagrees with the form. In round 2 the form favoured Aims, but the count of components reopened or discarded favoured OpenSpec in five of six readings.
  • cost Round 2, per product: Aims used 8–13 million tokens, 26–49 minutes and $12–21, Workers included. OpenSpec used 1.6–2.2 million tokens and 6–7 minutes.

Study 2: adding features to existing code

Five experiments added a feature to existing code, comparing Aims with an agent without the method. One of them used a real open-source module.

  • equal Correctness: the agent without the method added the feature correctly every time, and the method caught no bug the other agent missed. For a feature that fits in one session, Aims is not needed for correctness.
  • sequence Over a sequence of three additions a judge found the Aims code getting cleaner at each step while the other arm's code grew denser. The coupling measure did not confirm this: by that measure both arms got worse, Aims slightly less so.
  • style Existing style: when the existing code was written in a plain style, Aims kept that style instead of imposing its own.
The bottom line

What we could not show, and why

The paper set out to show that making design the objective produces better code. It could not show it, and the reason is measurement, not a result in either direction.

Judges do not agree

The same designs received grades from 5.7 to 9.8 depending on the judge, and correctness failures found by one judge were missed by another. Most differences between the methods were smaller than this spread.

Blinding is not possible

Each method leaves its own marks in its output, and every judge recognized them. A judge who knows which design came from which method is not blind, whatever the protocol says.

The form shares a source with the method

The form is built from the principles Aims designs toward, so it is likely to favour Aims. The one measure independent of those principles favoured the other tool.

No outside measure exists

There is no accepted benchmark or independent judge for design quality, and the automatic metrics measure size and branching, which good structure often increases.

What would be needed. The paper names three things, and none exists yet:
  • a measurement of how much independent judges agree, run on the same designs;
  • a way to hide which method produced a design, for example by rewriting every design into one neutral format before judging;
  • an outcome that depends on no rubric, such as the cost of a long sequence of later changes, measured over more changes than one session can hold.

The argument for making design the goal may still be right; it has not been tested. What is missing is a way to measure design quality that gives the same answer twice. Building one is the next step, before any further claim about Aims.
