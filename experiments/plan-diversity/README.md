# Experiment — where should PLAN-phase diversity come from? (blind, metrics fixed in advance)

A **method-internal experiment** run in the spirit of [`../PROTOCOL.md`](../PROTOCOL.md), but it is **not**
an aims-arm-vs-clean-arm build pilot. Every arm here *is* an aims PLAN pass; the single variable under test
is **where the design diversity comes from** before the candidates are collapsed into one design. It exists
to answer a question the method should not answer by taste:

> **Q — diversity source.** To reach the best *design* for one objective, does it help to run the PLAN pass
> three times — and if so, does the gain come from **different runs of one model** (sampling), from
> **different models**, or from **different instructions (stances) on one model** — or does none of it beat
> a single pass?

This is the "do we need a different source, a different instruction, or just *n* runs?" question, made to
discriminate.

---

## What is designed (the objective), and why it can discriminate

Diversity only matters when reasonable architectures genuinely diverge, so the objective must have real
architectural degrees of freedom and a nameable axis. The pilot reuses a product this repo already specifies:
the **instance-segmentation annotator** ([`../instance-seg-annotator/`](../instance-seg-annotator/)), whose
documented seam is *annotation geometry vs. how the image is presented/stored* (Stage 2 introduces satellite
tiling + a training-set export). The brief given to every arm is a **design** objective (Kind = `design`; no
runnable code required) for that full product **including** the tiling/export evolution — so a good vs. a
weak design differ on a structural axis the judge can reproduce, not on polish.

`n = 1` objective is *suggestive*, never robust (PROTOCOL §7). A second objective on a different axis is
listed under [Scaling](#scaling-beyond-the-pilot); the honest strength is any effect that recurs across both.

## Freeze the package before any arm runs

Do not edit mid-run:

1. **The sharpened brief** (`brief/brief.md`) — produced once via `/aims-sharpen-prompt`, then **frozen**.
   Identical for every arm and the baseline. It states the full product (both stages) as a design task and
   names the exit criteria the design must satisfy. It does **not** name the seam.
2. **The frozen rubric** (`judge/rubric.md`) — see [The judge](#the-judge-fable-blind-scored). Generated by
   the judge from the brief **before any candidate exists**, then frozen. Reusing it across all arms is what
   keeps the scoring comparable.
3. **The pinned method commit** — record the `aims-guide` / repo commit each PLAN pass ran under. The skill
   changes; "which aims" is part of the result.
4. **One equal ceiling** per candidate pass (turns / tokens / wall-clock). The extra passes an arm spends
   **are the treatment** — recorded, never equalized away.

## The arms — identical pipeline, one variable

Every arm runs the same two-stage pipeline. **Only the candidate-generation step differs**; the collapse step
is held constant so the candidate *source* is the only thing that varies among A/B/C.

| | Candidates generated | Collapse to one design |
|---|---|---|
| **Baseline** (control) | **1** pass — base model, neutral prompt | none (the single design *is* the output) |
| **A — intra-model** | **3** passes — base model, neutral prompt, independent (no pass sees another), sampling variation only | shared collapse ↓ |
| **B — inter-model** | **3** passes — **Sonnet · Opus · Fable**, neutral prompt, independent | shared collapse ↓ |
| **C — stance-seeded** | **3** passes — base model, each biased on a **real axis** (e.g. *minimize moving parts* / *maximize extension* / *optimize for testability*) | shared collapse ↓ |

- **Base model** (baseline, A, C): one strong model, pinned and held constant — **Opus**.
- **Shared collapse** (A, B, C): the identical cross-examination pass — same model (**Opus**), same prompt —
  reads the three candidate designs and emits **(i)** one final design and **(ii)** a `divergence-map.md`:
  where the candidates agreed (robust) and where they split (the real decision points). The map is not
  overhead — it is exactly the co-located design knowledge that belongs in `decisions/`.
- **Why hold collapse constant:** it makes **A vs. C** isolate *stance-seeding* (model held constant) and
  **A vs. B** isolate *model diversity* (prompt held constant). The baseline deliberately answers a coarser,
  prior question — *does three-plus-collapse beat one pass at all?* — and so carries no collapse by design.

## Controlled variables

Hold constant across every arm: model + version and reasoning/budget setting (per the roles above), the
frozen brief and exit criteria, the collapse model + prompt, tool/permission substrate, and the judge (which
built none of the designs). Independence is enforced: no candidate pass sees another's output; the judge sees
no arm labels.

## The judge (Fable), blind, scored

The measure is **design quality in software-engineering terms**, and the judge is **Fable**. The whole point
is **clear metrics fixed in advance** — declared before any design is seen, then measured against, one by one.
This is deliberately *not* a bare "judge it": an intuitive "this looks good" is neither a correct measurement
nor a neutral one (a model drifts toward its own idiom). The fixed metric list is itself the fix. Three guards:

1. **Rubric generated once, before candidates exist, then frozen.** Fable is given only the brief + exit
   criteria and produces `judge/rubric.md` by **selecting and instantiating the applicable principles from
   [`../../skills/aims-guide/references/design-principles.md`](../../skills/aims-guide/references/design-principles.md)**
   for this objective — *not* inventing axes. For each selected principle it writes a one-line question, a
   **0–5 scale**, and what a 0 vs. a 5 looks like *for this product*. Grounding in the 12 principles is what
   keeps "judge-generated" from drifting into taste. Optionally, you approve the rubric before scoring.
2. **The same frozen rubric for every arm** in this objective. (A different objective may get a different
   rubric — design quality is partly task-specific — but within an objective it is fixed.)
3. **Blind, and every reading is structural — never by feel.** The final designs are anonymized
   (method-revealing names stripped), relabeled and shuffled. Fable scores each metric 0–5 **only with a
   reading that points to a concrete structural fact a human could reopen and confirm** — the `section` where
   the invariant is owned once (or split), where a boundary is one seam (or N), where an implementation type
   leaks the export format. A reading that rests on wording, tone, or "reads cleanly" is **void — dropped,
   not counted** (PROTOCOL §6.3: a verdict turns on a structural property; a removable local blemish must not
   flip it).

**The measurement is the per-metric vector — a reading per frozen metric, per arm. That vector is the
finding.** No summed composite is needed to run the experiment: the arms are compared **metric by metric**
(on which arm's design owns the invariant once, draws the boundary as one seam, keeps the export format
behind a domain type, and so on). An overall total may be tallied as a convenience glance, but it is never
the verdict — a design can lead on a total and lose a load-bearing axis (say testability), and reporting that
trade-off honestly is the whole value of keeping the axes separate.

**Reliability of the instrument itself:**
- **Rubric stability** — regenerate the rubric 2–3× from the same brief; measure overlap of the selected
  metric set. An unstable metric list is a finding about the method's robustness, not a nuisance.
- **Score stability** — re-score 2–3× with re-shuffled labels; check for score drift and position bias. If
  Fable is not consistent with itself, the arm differences are noise — itself a result worth reporting.

## Confounds & mitigations

- **Judge self-preference (Fable generates a candidate in Arm B *and* judges).** Held down by the fixed
  metric list + reproduced-or-cite readings (a self-style preference cannot masquerade as a structural fact)
  plus blinding, author-stripping and shuffle. Declared as a standing caveat, concentrated in Arm B — not
  claimed removed; if a reading ever looks like taste, you spot-check that one.
- **Synthesizer confound.** The collapse model (Opus) is held constant across A/B/C, so it cancels in the
  A↔B and A↔C comparisons; the baseline lacks it *by design* and answers only the coarser question.
- **Stochastic noise.** `n ≥ 2` per arm per objective where budget allows; a second objective for recurrence.
- **Rubric gaming / drift.** Frozen before candidates, grounded in the 12 principles, stability-checked.

## Interpretation rules, fixed in advance

Compare the arms **metric by metric** (below, "≥" means "leads on the frozen metrics, with readings"); report
axis trade-offs as trade-offs rather than collapsing them.

- **Baseline ≈ A ≈ B ≈ C** → diversity does not help *design* for this objective; a single PLAN pass suffices.
- **A ≥ Baseline, but B ≈ A and C ≈ A** → plain repetition is the active ingredient. **"Just run *n* times."**
- **C ≥ A (model held constant), B ≈ A** → *instruction/stance* diversity is what works — and **model
  diversity (multiple subscriptions) is not needed.**
- **B ≥ A and B ≥ C** → *model* diversity is doing real work; multiple models earn their cost.

No single run decides it. The honest reading is any ordering that **recurs across objectives**; `n = 1` is
suggestive.

## Artifacts to keep (so the judge can be audited)

Per objective: the frozen brief; per arm, the 3 candidate designs + the final design + `divergence-map.md`;
the frozen rubric + its regenerations; the per-metric score sheets with each reading's reproduction/citation;
the shuffle/label logs; the cost logs; the pinned method commit; and a `results.md` verdict — the totals, the
vectors, the reliability readings, and the honest limits.

## The pilot (do this first)

Run **one** objective (the instance-seg annotator design) end-to-end at `n = 1` — **Baseline + A + C first**
(both on the base model: cheapest, and they answer the question you care most about — *n-runs vs. stances*).
Add **B** once the pipeline holds. The pilot's real purpose is to prove the instrument before scaling: freeze
the brief, generate + freeze the rubric, check that Fable's rubric and scores are **stable across re-runs**,
and confirm the blind/shuffle actually hides arm identity. If the judge is not self-consistent on one
objective, fix that before spending on a second.

## Scaling beyond the pilot

Add a second objective on a **different** architectural axis (a late-introduced identity/ownership rule, or a
delivery/format boundary) and raise to `n ≥ 2` per arm. Report the ordering that recurs — not the win tally.
